# راهنماهای جامع عملیاتی و ران‌بوک‌های بحران (Operational Runbooks) — نسخه v2.2.0

این مستند حاوی دستورالعمل‌های گام‌به‌گام و فرامین اجرایی دقیق برای تیم‌های عملیات (DevOps/SRE)، بک‌اند و پشتیبانی در مواجهه با رخدادهای سیستمی و مدیریت چرخه حیات پلتفرم **DERMAVIA Brand Commerce** است.

---

## ۱. سطوح شدت رخداد (Incident Severity Classification)

| سطح شدت | تعریف و آستانه تاثیر | حداکثر زمان واکنش (SLA) | نمونه‌های رخداد |
|---|---|---|---|
| **SEV-1 (بحرانی)** | نقض تمامیت مالی، نشت PII، یا از دست رفتن دسترسی پایگاه داده | **کمتر از ۱۵ دقیقه** | عدم کارکرد دیتابیس، نشت کلیدهای سازمانی، مغایرت ارزی |
| **SEV-2 (حاد)** | اختلال در گلوگاه‌های اصلی سفر مشتری (پرداخت، ثبت سفارش یا تسویه‌حساب) | **کمتر از ۳۰ دقیقه** | خطای وب‌هوک پرداخت، بن‌بست رزرو موجودی |
| **SEV-3 (متوسط)** | اختلال در بخش‌های غیراصلی یا بخش اداری با وجود مسیر جایگزین | **کمتر از ۴ ساعت** | تاخیر در پیش‌نمایش گراف، خطای آپلود مدارک فرم B2B |
| **SEV-4 (جزئی)** | ایراد بصری جزئی، خطای تایپی یا کندی غیربحرانی | **در اسپرینت جاری** | حاشیه بصری دکمه‌ها، عدم تقارن در رزولوشن‌های خاص |

## ۲. ران‌بوک‌های عملیاتی استاندارد

### RB-01: پشتیبان‌گیری و بازیابی پایگاه داده (Database Backup & Point-in-Time Recovery)
- **مالک:** مهندس زیرساخت / DevOps
- **شدت فعال‌سازی در بحران:** SEV-1
- **پیش‌نیازها:** دسترسی CLI به سرور پایگاه‌داده PostgreSQL 16.

#### فرامین پشتیبان‌گیری (Backup):
```powershell
# ایجاد پوشه پشتیبان با برچسب زمانی
$timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$backupFile = "backups/brand_commerce_$timestamp.sql"

# اجرای پشتیبان‌گیری کامل پایگاه داده همراه با تعاریف اسکیما و لجرها
cmd /c "pg_dump -U postgres -h localhost -p 5432 -F c -b -v -f $backupFile brand_commerce"

# تولید هش اعتبارسنجی یکپارچگی فایل
Get-FileHash $backupFile -Algorithm SHA256 | Out-File "$backupFile.sha256"
```

#### فرامین بازیابی اضطراری (Restore):
```powershell
# ۱. متوقف‌سازی موقت سرویس‌های مصرف‌کننده (API)
cmd /c "cd brand-commerce && taskkill /F /IM node.exe"

# ۲. اعتبارسنجی سلامت فایل پشتیبان
Get-FileHash $backupFile -Algorithm SHA256

# ۳. بازیابی به پایگاه داده هدف
cmd /c "pg_restore -U postgres -h localhost -p 5432 -d brand_commerce -v --clean $backupFile"

# ۴. اعتبارسنجی سلامت سرویس پس از بازیابی
cmd /c "cd brand-commerce && node apps/api/dist/main.js"
curl http://localhost:3001/api/v1/health
```

### RB-02: تعویض اضطراری کلیدها و اسرار (Credential & Key Rotation)
- **مالک:** تیم امنیت و مهندس ارشد بک‌اند
- **شدت فعال‌سازی:** SEV-1 / SEV-2

#### ۱. تعویض کلید مدیریت اپراتور (`ADMIN_API_KEY`):
1. ایجاد کلید جدید پرآنتراپی ۶۴ کاراکتری در محیط:
   ```powershell
   # تولید رشته تصادفی امن
   $newKey = [Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Maximum 256 }))
   ```
2. به‌روزرسانی متغیر `ADMIN_API_KEY` در فایل‌های محیطی سرور (`.env`).
3. بازنشانی متغیرها با ری‌استارت امن پراسس API:
   ```powershell
   cmd /c "cd brand-commerce && node apps/api/dist/main.js"
   ```
4. تمامی نشست‌های ادمین قبلی بلافاصله ۴۰۱ دریافت می‌کنند.

#### ۲. ابطال اضطراری کلید دسترسی عضو سازمانی B2B (`x-org-key`):
1. ورود به کنسول مدیریت اپراتور در `/admin`.
2. رفتن به تب **«سازمان‌ها و اعضا»**.
3. کلیک روی دکمه **«ابطال کلید»** در ردیف عضو مورد نظر (تنظیم فیلد `keyRevokedAt` در دیتابیس).
4. هرگونه درخواست بعدی با این کلید بلافاصله خطای `403 Forbidden` با پیام فارسی «کلید سازمانی باطل شده است» دریافت می‌کند.

### RB-03: رفع مغایرت لجر و هم‌زمانی انبارداری (Inventory Ledger Reconciliation)
- **مالک:** اپراتور انبارداری و مهندس پایگاه داده
- **شدت فعال‌سازی:** SEV-2
- **قاعده حاکمیتی:** موجودی فیزیکی و اسناد لجر اصل حقیقت هستند؛ تغییر مستقیم ستون `onHand` بدون ردیف لجر اکیداً ممنوع است.

#### مراحل بررسی و تسویه:
1. استعلام موجودی اسمی در برابر جمع حرکات لجر:
   ```sql
   SELECT 
     "variantId",
     "onHand",
     "reserved",
     (SELECT COALESCE(SUM(quantity), 0) FROM "InventoryLedger" WHERE "variantId" = i."variantId") as ledger_sum
   FROM "InventoryItem" i;
   ```
2. در صورت وجود انحراف، وارد کنسول اپراتور `/admin` شده و به تب **«انبارداری و لجر»** بروید.
3. با انتخاب واریانت و مقدار کسری یا مازاد، فیلد «دلیل اصلاح موجودی» را تکمیل کرده و دکمه **«ثبت اصلاحیه انبار»** را بزنید.
4. تراکنش اتمیک یک ردیف جدید از نوع `ADJUSTMENT` در جدول `InventoryLedger` درج کرده و موجودی اسمی را همگام می‌سازد.

### RB-04: مدیریت استرداد وجه و رخدادهای وب‌هوک (Payment Refund & Webhook Recovery)
- **مالک:** تیم مالی و پشتیبانی فنی
- **شدت فعال‌سازی:** SEV-2 / SEV-3

#### گام‌های استرداد وجه سندباکس:
1. در پنل ادمین `/admin` یا صفحه سفارش `/orders/[id]`، شناسه پرداخت سفارش تأییدشده (`PAID`) را بردارید.
2. ارسال رکوئست استرداد وجه به درگاه:
   ```bash
   curl -X POST http://localhost:3001/api/v1/payments/{paymentId}/refund \
     -H "Content-Type: application/json"
   ```
3. اعتبارسنجی خودکار تراکنش در پایگاه داده:
   - وضعیت پرداخت به `REFUNDED` تغییر می‌یابد.
   - وضعیت سفارش به `REFUNDED` تغییر می‌یابد.
   - اقلام کاتالوگ به‌صورت خودکار با یک ردیف `RESTOCK` به موجودی فعال انبار بازمی‌گردند (اقلام OEM از این فرآیند مستثنی هستند).

### RB-05: استقرار ایمن و رول‌بک بدون قطعی (Zero-Downtime Deployment & Rollback)
- **مالک:** DevOps / مهندس استقرار
- **رویکرد حاکمیتی:** الگوی Two-Phase Expand-and-Contract.

1. **فاز Expand (گسترش اسکیما):**
   - مایگریشن‌های جدید همواره باید سازگار با کدهای نسخه قبلی باشند (ستون‌های جدید الزامی نباشند یا مقدار Default داشته باشند).
   - اجرای مایگریشن در خط لوله:
     ```bash
     npm run migrate:deploy -w @bc/database
     ```
2. **فاز Deploy:**
   - استقرار بیلد جدید API و Storefront.
3. **فرمان رول‌بک اضطراری کد در صورت بروز کرش:**
   ```bash
   git checkout main~1
   npm run build
   # اجرای سرور با بیلد پایدار قبلی
   npm run verify
   ```
